提炼这篇文章中的技术，用简单的案例做分析演示

---

这篇文章真正值得提炼的，不是一个新的“评分算法”，而是一套 **Agent 化评测架构** ：把传统的“固定题目 + 固定指标 + 一个分数”，升级成“先理解任务 → 动态选择评测能力 → 多 Agent 找证据 → 交叉验证 → 输出可审计结论”的 Harness。

文章把这个思路称为 **HarnessEval** ，核心目标是让 Evaluator 本身也成为一个可以调用工具、拆解任务、持续补充 Skill 的智能体系统。

---

传统评测：

```
模型输出
   ↓
固定规则
   ↓
计算分数
   ↓
85 分
```

HarnessEval：

```
模型输出
   ↓
Evaluator Agent 先理解任务
   ↓
动态选择 Skill
   ↓
拆成多个可验证问题
   ↓
派生多个 SubAgent
   ↓
调用工具寻找证据
   ↓
交叉验证
   ↓
Evidence Tree
   ↓
评分 + 失败原因 + 证据
```

文章给出的完整过程基本就是四步：

所以它实际上更像一个：

> **Evaluation Agent Operating System**

而不是传统 benchmark。

## 二、文章里最核心的 9 项技术

## 1\. Harness：把评测变成“工作流”

Harness 在这里不是简单代码 wrapper，而是：

> 把问题分解、工具调用、推理验证组织成清晰、可执行步骤的框架。

它解决的关键问题是：

```
Agent知道什么
Agent下一步做什么
调用哪个工具
结果交给谁
什么时候继续拆解
什么时候停止
最后如何验证
```

可以把 Harness 理解为：

```
LLM
+
Workflow
+
Tool
+
Skill
+
Validator
+
State
+
Evidence
```

这和单纯让模型 Prompt：

```
请你检查一下这个答案对不对
```

完全不是一个层级。

## 三、案例 1：评测一个代码 Agent

假设给代码 Agent 一个任务：

```
写一个 Python 函数：

def divide(a, b):
    ...

要求：
1. 返回 a / b
2. b=0 时不能崩溃
3. 输入不是数字时要报错
```

Agent 给出了：

```python
def divide(a, b):
    return a / b
```

传统评测可能只有：

```
测试：
divide(10,2) == 5

通过 ✅

Score = 100
```

问题来了：

它其实没有处理：

```
divide(10, 0)
divide("10", 2)
```

---

## HarnessEval 怎么评？

首先 Main Evaluator 判断：

```
这是代码生成任务。
```

于是动态选择：

```
Skill:
├─ FunctionalCorrectness
├─ EdgeCaseTesting
├─ ExceptionHandling
└─ CodeQuality
```

这就是文章所谓：

> 不同行业沉淀不同 Skill，并形成可组合、可版本化的 Skill Library。

## 四、技术 2：Dynamic Skill Selection

HarnessEval 最大变化之一：

> **不是所有案例都跑所有指标。**

先判断：

```
这个任务真正需要检查什么？
```

文章明确说，系统先理解目标和上下文，再选择真正相关的评测能力。

刚才代码案例可能动态选择：

```
divide()

目标：
正确计算除法

↓ Evaluator

需要检查：

✓ 正确性
✓ 除零
✓ 类型检查
✓ 异常处理

不需要：

× UI
× 网络性能
× 数据库
× 并发
```

逻辑可以抽象成：

```python
skills = skill_router.select(task)

for skill in skills:
    evaluate(skill)
```

例如：

```python
if task.type == "code":
    skills = [
        FunctionalTest,
        EdgeCaseTest,
        ExceptionTest
    ]
```

但真正的 Harness 不一定靠死规则，可以让 Agent 动态判断。

## 五、技术 3：Task Decomposition

这是第二个关键能力。

不是问模型：

```
这个函数好吗？
```

因为这是一个模糊问题。

而是拆成：

```
divide() 是否正确？
    │
    ├─ 正常输入是否正确？
    │
    ├─ b = 0 会怎样？
    │
    ├─ 字符串输入会怎样？
    │
    └─ 异常信息是否合理？
```

即：

```
复杂判断

↓

多个原子判断
```

文章在世界模型的例子里也是这么做的：

判断碰撞是否合理，继续拆成：

```
物体位置
接触时间
碰撞前速度
碰撞后速度
```

而不是让一个模型直接回答“碰撞合理 / 不合理”。

## 六、技术 4：SubAgent 动态派生

这一步很重要。

Main Agent 不是什么都自己判断，而是动态创建不同专家。

例如：

```
Main Evaluator
      │
      ├── Functional Agent
      │
      ├── Edge Case Agent
      │
      ├── Exception Agent
      │
      └── Security Agent
```

分别负责：

### Functional Agent

运行：

```python
divide(10, 2)
```

结果：

```
5
```

结论：

```
PASS
```

---

### Edge Case Agent

运行：

```python
divide(10, 0)
```

得到：

```
ZeroDivisionError
```

发现：

```
FAIL
```

---

### Type Agent

运行：

```python
divide("10", 2)
```

发现：

```
TypeError
```

但题目要求主动检查类型，因此：

```
FAIL
```

文章明确描述：每一个 Skill 都可以进一步衍生一系列 subagents，从不同角度衡量模型能力。

## 七、技术 5：Tool-Augmented Evaluation

这可能是整个设计最容易被忽略、但最重要的东西。

传统：

```
LLM Judge

“我觉得这个答案是 8 分。”
```

HarnessEval：

```
LLM Judge
    │
    ├─ Python
    ├─ Test Runner
    ├─ Browser
    ├─ Object Detection
    ├─ Tracking
    ├─ SQL
    ├─ Search
    └─ External API
```

文章在世界模型里举的就是：

```
目标追踪
时序分析
速度估计
```

不同 SubAgent 调用不同诊断工具获取证据。

也就是说：

> Evaluator 不应该单靠“语言感觉”评分，而应该尽量把判断转化成工具可以验证的事实。

这是非常重要的架构原则。

## 九、技术 6：Evidence Tree

这是我认为文章中最值得落地的一项技术。

HarnessEval 最终不只输出：

```
Score = 72
```

还生成：

```
Evidence Tree
```

文章强调：

> 测了什么、调用了什么工具、找到什么证据、结论如何产生，都可以逐层展开。

例如代码 Agent：

```
divide函数评测
│
├─ Functional Correctness ✅
│   │
│   └─ test(10,2)
│       ├─ Expected: 5
│       └─ Actual: 5
│
├─ Zero Division ❌
│   │
│   └─ test(10,0)
│       ├─ Expected: Graceful handling
│       └─ Actual: ZeroDivisionError
│
└─ Input Validation ❌
    │
    └─ test("10",2)
        ├─ Expected: Explicit validation
        └─ Actual: TypeError
```

最终：

```
Score: 63

核心缺陷：
1. 未处理除零
2. 未进行输入检查
```

于是评测从：

```
评分系统
```

升级成：

```
诊断系统
```

文章总结得很准确：

> 分数用来排名，证据用来诊断、审计和复核。

## 十、技术 7：Agent 自动“出题”

传统 Benchmark：

```
dataset.json

Q1
Q2
Q3
...
Q1000
```

生成一次之后基本冻结。

HarnessEval：

```
Scenario Generator
        ↓
生成新场景
        ↓
Validation Agent
        ↓
检查：
目标明确吗？
任务可执行吗？
结果可验证吗？
        ↓
不合格 → Reject
        ↓
重新生成
```

文章里明确说，Benchmark 的数据集构建也由 Agent 参与：

> 系统生成候选场景和动作，再由独立 Validation Agent 检查；不合格案例退回重新生成。

因此：

```
Evaluator
既是阅卷老师

又是出题老师

还带一个质检员。
```

## 十三、技术 9：Test-Time Scaling for Evaluation

这是文章一个很重要的判断：

> 被评模型越强，Evaluator 也必须越强。

文章称 Harness 可以让模型获得 Test-Time Scaling：

复杂任务投入：

```
更多 Token
更多推理
更多工具
更多 Agent
更多验证步骤
```

Evaluator 同样如此。

简单题：

```
2 + 2 = ?

Evaluator
└─ Calculator
```

复杂题：

```
某 AI Agent 是否完成一次企业并购研究？
```

可能变成：

```
Evaluator
│
├─ Financial Agent
│
├─ Legal Agent
│
├─ Source Agent
│
├─ Calculation Agent
│
├─ Contradiction Agent
│
├─ Risk Agent
│
└─ Final Verification Agent
```

这就是 Evaluation 的 Test-Time Scaling。

## 十四、RSI：为什么文章一直强调它

文章里的 RSI 指：

```
Recursive Self-Improvement
递归式自我改进
```

基本循环：

```
Agent执行
   ↓
Evaluator评估
   ↓
发现问题
   ↓
Agent修改
   ↓
再次执行
   ↓
再次评估
   ↓
继续改进
```

即：

```
Build
 ↓
Run
 ↓
Evaluate
 ↓
Diagnose
 ↓
Improve
 └─────────┐
           ↓
          Run
```

问题在于：

> 如果 Evaluator 本身很弱，自我改进方向就可能错。

文章特别指出：

```
评测奖励什么
↓
Agent 就强化什么

评测忽略什么
↓
盲点可能越来越严重
```

这和强化学习里的 reward hacking 非常类似。

## 十七、一个最简单的伪代码

整个框架其实可以浓缩成：

```python
def evaluate(task, output):

    # 1. 理解任务
    context = understand(task)

    # 2. 动态选择评测技能
    skills = skill_router.select(context)

    evidence_tree = []

    for skill in skills:

        # 3. 拆解
        checks = skill.decompose(task, output)

        for check in checks:

            # 4. 创建专业 evaluator
            agent = spawn_subagent(check)

            # 5. 调工具找证据
            evidence = agent.investigate(
                tools=skill.tools
            )

            evidence_tree.append(evidence)

    # 6. 交叉验证
    result = verifier.verify(
        evidence_tree
    )

    return {
        "score": result.score,
        "decision": result.decision,
        "evidence": evidence_tree
```

真正值得关注的不是这段代码，而是其中这几个抽象：

```
Skill Router
Task Decomposer
SubAgent
Tool
Evidence
Verifier
```

## 十八、如果套到你一直研究的 Harness Engineering，可以这样理解

我认为 HarnessEval 和你之前关注的 Harness Engineering 可以统一成一个更大的框架：

```
Harness
                       │
       ┌───────────────┴──────────────┐
       ↓                              ↓
Execution Harness               Evaluation Harness
执行 Harness                     评测 Harness
       │                              │
Planner                         Eval Planner
       ↓                              ↓
Skill                           Eval Skill
       ↓                              ↓
SubAgent                        Eval SubAgent
       ↓                              ↓
Tool                            Diagnostic Tool
       ↓                              ↓
Validator ───────────────────→ Evidence
       ↓                              ↓
Output                          Verification
       │                              │
       └──────── Feedback Loop ───────┘
```

于是形成：

```
┌────── EXECUTE ──────┐
    ↓                      │
Agent Harness              │
    ↓                      │
  Output                   │
    ↓                      │
Eval Harness               │
    ↓                      │
 Evidence                  │
    ↓                      │
Diagnosis                  │
    ↓                      │
Improvement ───────────────┘
```

这才是文章所谓 RSI 闭环真正重要的地方：评测不再位于系统末端，而开始成为智能体自我改进循环本身的一部分。

如果你要设计自己的 Agent 系统，这套链路甚至可以同时承担 **执行审计、Validator、质量控制和评测** ，比简单的“一个主 Agent + 一个 Validator”更完整。文章本身也明确把 Harness 的目标定义为把“问题、技能、证据和验证”组织成可信判断。
