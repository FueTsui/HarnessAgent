# 为什么低能力模型使用 Harness 效果不好？

先看 Harness 的标准流程：

```
用户任务
     │
 Planner
     │
 Executor
     │
 Tool
     │
 Reflection
     │
 Judge
     │
 Retry
```

GPT-5 在每个节点都能稳定工作。

例如：

Planner：

```
应该拆成四个步骤
```

Executor：

```
先执行 Tool A
再执行 Tool B
```

Reflection：

```
Tool B 输出异常
需要重新执行
```

Judge：

```
测试没有通过
```

Retry：

```
修改方案
重新执行
```

整个流程都比较稳定。

------

但 GPT-OSS 这类模型通常不是这样。

例如 Planner：

```
不知道怎么拆
```

Reflection：

```
看不出来哪里错
```

Judge：

```
测试失败

↓

仍然认为成功
```

Retry：

```
重复第一次方案
```

于是：

Harness 没有发挥作用。

反而：

越来越慢。

Token越来越多。

错误越来越多。

------

## 为什么？

因为 Harness 默认假设：

> **模型能够理解整个 Workflow。**

但是：

GPT-OSS 很多时候：

连当前一步都容易理解错。

所以：

不是 Harness 有问题。

而是：

**Harness 太相信模型。**

------

# GPT-OSS 最大的问题不是知识，而是控制能力

很多测试发现：

GPT-OSS：

知识：

★★★★☆

推理：

★★★☆☆

工具使用：

★★☆☆☆

长期规划：

★☆☆☆☆

状态维护：

★☆☆☆☆

反思能力：

★☆☆☆☆

这意味着：

真正应该补的不是：

知识。

而是：

**控制能力(Control Ability)。**

------

# 那应该怎样升级 Harness？

我认为未来会出现一种新的方向：

> **Small Model Harness（SMH）**

不是：

让模型负责全部。

而是：

把大量决策收回 Harness。

下面我认为有几个方向。

------

# 第一：把 Planner 拆掉（最重要）

现在很多 Agent：

```
Planner

↓

生成完整计划

↓

Executor
```

GPT-5 可以。

GPT-OSS 不行。

建议：

改成：

```
Task

↓

Step Generator

↓

一步

↓

执行

↓

再生成下一步
```

不要：

一次规划：

十步。

改成：

每次：

只规划一步。

例如：

不要：

```
修改整个项目
```

而是：

```
第一步：

找到Bug。

↓

完成。

↓

第二步：

修改Bug。

↓

完成。

↓

第三步：

运行测试。
```

为什么？

因为：

小模型：

更适合：

短期规划。

------

# 第二：Harness 接管 Reflection

很多 Harness：

Reflection：

还是：

LLM。

例如：

```
为什么失败？
```

GPT-OSS：

回答：

```
可能网络不好。
```

其实：

真正原因：

```
404
```

所以：

不要：

让模型分析日志。

改成：

Harness：

直接：

解析：

```
ExitCode

HTTP

stderr

stdout

pytest
```

例如：

```
pytest:

FAILED

↓

Harness：

定位：

test_login.py

Line 83

↓

告诉模型：

修这里。
```

而不是：

把：

1000行日志：

交给模型。

------

# 第三：增加 Rule Engine（规则引擎）

很多判断：

根本不需要模型。

例如：

```
Git 有没有冲突？

↓

Git自己知道。
Docker 是否启动？

↓

Docker自己知道。
文件是否存在？

↓

OS知道。
HTTP是不是200？

↓

程序知道。
```

所以：

Rule Engine：

应该越来越强。

模型：

越来越少判断。

------

# 第四：状态压缩（Memory Compression）

GPT-OSS：

上下文：

容易爆。

所以：

不要：

全部Memory。

建议：

每一步：

自动：

压缩。

例如：

原来：

```
100KB
```

变成：

```
当前状态：

已完成：

1

2

3

失败：

4

下一步：

5
```

而不是：

一直：

追加。

------

# 第五：Tool Router

GPT-OSS：

最容易：

工具乱选。

例如：

200个Tool。

模型：

不知道：

调用哪个。

建议：

增加：

Tool Router。

流程：

```
全部Tool

↓

Router

↓

候选：

3个

↓

模型选择
```

这样：

准确率：

会高很多。

Router 可以依据工具描述、历史成功率、输入类型甚至向量检索来筛选，而不是让模型面对几十甚至几百个工具。

------

# 第六：模板化 Tool 调用

很多模型：

不是不会。

而是：

不会写参数。

例如：

应该：

```
{
  "path":"test.py",
  "recursive":true
}
```

GPT-OSS：

写：

```
{
 "file":"test"
}
```

因此：

Harness：

应该：

自动：

补全。

甚至：

提供：

固定模板。

模型：

只填：

变量。

这类似于将 Tool 调用从"自由生成"变成"结构化填空"。

------

# 第七：把 Retry 变成 Search

现在：

Retry：

```
失败

↓

模型：

再想一次
```

GPT-OSS：

通常：

还是：

同一种方案。

建议：

改成：

```
失败

↓

Harness

↓

搜索：

历史成功案例

↓

给模型
```

例如：

Memory：

```
去年：

出现过：

一样Bug。
```

模型：

直接：

参考。

这样：

Retry：

就变成：

Knowledge Retry。

而不是：

Blind Retry。

------

# 第八：增加 Expert Skill（专家 Skill）

未来：

Skill：

会越来越重要。

例如：

OCR。

不要：

让：

GPT-OSS：

推理：

OCR。

而是：

Skill：

告诉它：

```
OCR：

必须：

先：

Deskew

↓

Denoise

↓

Recognition
```

模型：

负责：

调度。

不是：

发明流程。

也就是说，Skill 本身携带领域知识和最佳实践，降低模型的推理负担。

------

# 第九：让 Harness 学习，而不是模型学习

目前：

很多Agent：

都是：

模型学习。

其实：

Harness：

也可以学习。

例如：

记录：

```
Tool A：

成功：

95%
Tool B：

成功：

12%
```

以后：

Router：

自动：

优先：

Tool A。

再例如：

```
这个Prompt：

连续：

失败：

20次。
```

自动：

降低：

权重。

这里学习的是**运行策略**，而不是修改模型参数。

------

# 第十：多模型分工（最有潜力）

我认为未来不会是：

> 一个 GPT-OSS 完成所有工作。

而是：

```
             Orchestrator（Harness）
                     │
 ┌────────────┬──────────────┬─────────────┐
 │            │              │
Planner     Tool Model     Judge Model
 │            │              │
Qwen3      GPT-OSS         小型Verifier
 │            │              │
 └────────────┴──────────────┘
                     │
                  Memory
```

甚至：

不同Skill：

绑定：

不同模型。

例如：

OCR：

Nemotron OCR。

代码：

DeepSeek。

规划：

Qwen。

验证：

专门Judge。

这样：

每个模型：

做：

最擅长的事情。

------

# 从更长远的角度看：Harness 会越来越"厚"

目前很多人认为：

```
Agent = LLM + Tool
```

我认为未来会变成：

```
                 Application
                      │
                Harness Runtime
──────────────────────────────────────
Workflow Engine
State Manager
Memory Manager
Rule Engine
Tool Router
Scheduler
Checkpoint
Evaluator
Policy Engine
Skill Library
Failure Analyzer
Execution Cache
Knowledge Retriever
──────────────────────────────────────
           Foundation Models
```

也就是说，**智能越来越来自 Runtime，而不是全部来自模型本身。**

------

# 我认为未来针对 GPT-OSS 这类模型的 Harness 设计原则可以概括为一句话

高能力模型（GPT-5、Claude）适合：

> **Think More（多思考，少约束）**

它们可以承担规划、反思、纠错等复杂认知任务。

而低能力模型（GPT-OSS、7B～32B 开源模型）更适合：

> **Think Less，Execute Better（少思考，多执行）**

Harness 应尽可能把**规划、规则判断、状态管理、工具选择、错误定位、经验复用**这些确定性工作从模型手中收回，用程序完成；模型只负责局部推理和生成。这种"厚 Runtime + 轻模型"的架构，比单纯提升模型参数规模，更有可能让中小模型在生产环境中获得稳定、可预测的表现。
