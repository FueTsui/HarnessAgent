# 一、先建立统一认识

这几个词都在描述同一个问题：

> **怎样把一个“会生成文字的模型”，改造成一个能够持续执行任务、调用工具、检查结果、处理失败并受到安全约束的智能体系统。**

它们分别控制不同层级：

```
┌──────────────────── Harness：运行环境与工程外壳 ────────────────────┐
│ 权限、工具、Skill、MCP、沙盒、记忆、日志、预算、评估、检查点、CI     │
│                                                                   │
│   ┌──────────────── Graph：系统执行拓扑 ──────────────────────┐   │
│   │                                                           │   │
│   │  [规划节点] → [执行节点] → [验证节点] → [审批节点]         │   │
│   │       │           │            │                           │   │
│   │       └──条件分支──┴────失败回退──┘                        │   │
│   │                                                           │   │
│   │          节点内部可以包含一个或多个 Loop                   │   │
│   │                                                           │   │
│   │   Model → Tool → Observation → Model → Tool → ...         │   │
│   └───────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────────┘
```

可以压缩成一句话：

- **Loop**：局部时间结构——下一轮怎么继续。
- **Graph**：全局空间结构——不同步骤怎么连接。
- **Graph Engineering**：如何设计和治理这些节点、路径、状态和循环。
- **Harness Engineering**：如何设计模型外部的完整运行系统，使它可靠工作。

截至 **2026年7月**，“Graph Engineering”和“Loop Engineering”仍属于快速形成中的行业术语，并不是像数据库工程、编译器工程那样已有稳定边界的传统学科。LangChain也把 Graph Engineering称为近期出现的行业术语，但认为它确实描述了真实的智能体架构问题。[LangChain](https://www.langchain.com/blog/3-years-of-graph-engineering-with-langgraph)

------

# 二、Graph：图

## 1. Graph的基本含义

图是一种由两类元素组成的结构：

```
Graph = Nodes + Edges
```

- **Node，节点**：执行某项工作。
- **Edge，边**：表示节点之间的连接、依赖或转移条件。

在普通软件中，节点可能是函数、任务、服务、数据处理阶段。

在AI智能体中，节点可以是：

- 一次LLM调用；
- 一个工具调用；
- 一段确定性代码；
- 一个完整Agent；
- 一个审批步骤；
- 一个检索、验证或评分器；
- 一个包含自身循环的子系统。

边则表示：

- 无条件进入下一步；
- 根据模型输出进行条件路由；
- 根据程序判断进行确定性路由；
- 失败后回退；
- 并行拆分；
- 汇总多个节点的结果；
- 返回前面的节点重新执行。

LangGraph将这类图描述为一种状态机：节点完成工作，边决定下一步，状态则在节点之间流动。[LangChain](https://www.langchain.com/blog/3-years-of-graph-engineering-with-langgraph)

------

## 2. AI Agent中的Graph不是单纯流程图

普通流程图主要用于“展示”；智能体Graph需要真正“执行”。

一个可执行Graph通常至少包含五个部分：

### 2.1 节点 Node

节点最好对应一个清晰、可测试的职责：

```
需求分析
代码搜索
修改代码
运行测试
安全审查
生成报告
```

一个节点的理想结构是：

```
输入状态 → 执行逻辑 → 输出状态
```

例如：

```
def run_tests(state):
    result = execute_test_command()
    return {
        "test_result": result,
        "tests_passed": result.exit_code == 0
    }
```

节点边界越清楚，系统越容易：

- 测试；
- 替换模型；
- 重试；
- 缓存；
- 并行执行；
- 定位故障；
- 设置权限。

------

### 2.2 边 Edge

边决定控制流：

```
执行测试
   │
   ├── 测试通过 ──→ 生成报告
   │
   └── 测试失败 ──→ 分析错误 ──→ 修改代码 ──→ 再次测试
```

边可以分为三种。

**确定性边**

```
if tests_passed:
    return "finish"
else:
    return "repair"
```

适合权限、金额、状态码、测试结果等明确规则。

**模型决策边**

```
让LLM判断：
- 需要检索资料
- 需要调用工具
- 信息已经充分
- 需要用户确认
```

适合开放性问题，但可预测性较低。

**外部信号边**

例如：

- 用户批准；
- 新邮件到达；
- Webhook触发；
- 定时任务启动；
- 数据库状态变化；
- CI返回结果。

------

### 2.3 状态 State

Graph不是只传递文本，而是传递结构化状态：

```
{
  "goal": "修复登录失败问题",
  "current_plan": [],
  "files_read": [],
  "modified_files": [],
  "test_results": [],
  "retry_count": 2,
  "approval_status": "pending",
  "budget_remaining": 3.25
}
```

状态设计决定了系统能否：

- 中断后恢复；
- 避免重复操作；
- 记录任务进度；
- 并行执行；
- 审计决策；
- 压缩上下文；
- 更换模型而不丢失任务。

**Graph的核心不是画箭头，而是定义状态如何变化。**

------

### 2.4 调度器 Scheduler

当Graph中出现并行、等待和回退时，需要调度器回答：

- 哪些节点已经满足执行条件？
- 哪些任务可以并行？
- 哪些节点正在等待外部输入？
- 节点失败后重试还是回退？
- 哪个节点拥有状态写权限？
- 系统从检查点恢复后从哪里继续？

因此，成熟的Graph更接近：

> 状态机 + 工作流引擎 + 任务调度器。

LangGraph将自身定位为用于长期运行、有状态智能体的低层编排运行时，并强调持久化执行、流式输出、人工介入以及确定性步骤与LLM步骤混合。[Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview)

------

### 2.5 终止条件

每条Graph路径必须有明确终点：

```
成功结束
失败结束
等待审批
预算耗尽
达到重试上限
任务取消
超时结束
```

没有终止条件的Graph，通常会演变成：

- 无限循环；
- 重复工具调用；
- Token持续增长；
- 外部系统重复写入；
- 无法判断任务到底是否完成。

------

## 3. 常见Graph拓扑

### 3.1 线性Graph

```
输入 → 检索 → 生成 → 检查 → 输出
```

适合稳定、步骤固定的工作：

- OCR处理；
- 文档转换；
- 数据清洗；
- 报告生成；
- 固定审批流程。

优点是简单、可预测，缺点是适应性弱。

------

### 3.2 条件路由Graph

```
                  ┌→ 法律检索Agent
用户问题 → 分类器 ┼→ 财务分析Agent → 汇总
                  └→ 技术支持Agent
```

适合：

- 多领域客服；
- 多知识库检索；
- 模型路由；
- 不同权限级别；
- 不同文件类型处理。

------

### 3.3 Planner–Executor Graph

```
目标
 ↓
规划器
 ↓
任务队列
 ↓
执行器
 ↓
进度检查
 ├─ 未完成 → 更新计划 → 执行器
 └─ 完成   → 输出
```

适合长任务：

- 软件开发；
- 深度研究；
- 项目规划；
- 多文件修改；
- 数据分析。

------

### 3.4 Generator–Verifier Graph

```
生成 → 验证
       ├─ 通过 → 输出
       └─ 失败 → 反馈 → 重新生成
```

适合：

- 代码生成；
- SQL生成；
- 法律文档；
- 合规审查；
- 数学解题；
- 报告质量控制。

------

### 3.5 Supervisor–Worker Graph

```
               ┌→ 搜索Agent
Supervisor ────┼→ 编码Agent
               ├→ 测试Agent
               └→ 审查Agent
                    ↓
                 Supervisor
```

适合多智能体协作，但要注意Supervisor可能成为：

- 性能瓶颈；
- 单点故障；
- 上下文膨胀点；
- 错误决策中心。

------

### 3.6 Map–Reduce Graph

```
大任务
  ↓
拆分
  ├→ 子任务1 ┐
  ├→ 子任务2 ├→ 聚合 → 验证
  └→ 子任务3 ┘
```

适合：

- 多文档总结；
- 大型代码库分析；
- 批量数据处理；
- 多来源调查；
- 并行网页检索。

------

## 4. Graph的主要用途

Graph主要解决五类问题：

### 可控性

把必须遵守的业务顺序写进结构，而不是只写在提示词里。

例如：

```
支付前必须：
身份验证 → 风险检查 → 用户确认 → 执行支付
```

这比提示模型“请务必先检查风险”可靠得多。

### 可观察性

每个节点都可以记录：

- 输入；
- 输出；
  -耗时；
- Token；
- 错误；
- 工具调用；
- 状态变化。

### 可恢复性

任务执行到第20步失败时，可以从第20步或最近检查点继续，而不必从头开始。

### 并发性

无依赖的任务可以并行运行。

### 确定性与智能性的混合

成熟系统通常不是“全部交给LLM”，而是：

```
确定性代码控制边界
LLM处理模糊判断
工具执行真实动作
验证器检查结果
```

LangGraph把这种“确定性路径与Agent步骤混合”视为Graph架构的重要价值。[Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview)

------

# 三、Loop：循环

## 1. Loop的本质

Loop是一个反馈控制结构：

```
观察 → 判断 → 行动 → 获取结果 → 再观察
```

最基本的Agent Loop是：

```
用户目标
   ↓
模型推理
   ↓
是否需要工具？
   ├─ 否 → 输出最终结果
   └─ 是 → 调用工具
              ↓
          返回工具结果
              ↓
          再次调用模型
```

Claude Agent SDK将其描述为：模型接收当前上下文，决定是否调用工具；工具结果返回模型；循环持续，直到模型不再请求工具并输出最终结果。[Claude](https://code.claude.com/docs/en/agent-sdk/agent-loop)

LangChain也将标准Agent描述为“模型调用工具，直到达到停止条件”。[Docs by LangChain](https://docs.langchain.com/oss/python/langchain/context-engineering)

------

## 2. Loop为什么重要

单次LLM调用基本上是：

```
输入 → 输出
```

它不能自然完成需要环境反馈的任务，例如：

```
运行代码
发现报错
读取报错
修改代码
再次运行
确认通过
```

Loop让模型能够根据真实反馈调整后续动作。

因此，Loop实现的是：

- 试错；
- 自我修正；
- 多步规划；
- 工具交互；
- 环境适应；
- 逐步完成长任务。

------

## 3. 四个层级的Loop

### 3.1 Agent Loop：执行循环

```
思考 → 调用工具 → 观察结果 → 再思考
```

例如编码Agent：

```
读取文件
→ 修改代码
→ 运行测试
→ 查看错误
→ 再修改
→ 测试通过
```

这是最内层循环。

------

### 3.2 Verification Loop：验证循环

外面再套一层：

```
Agent执行
   ↓
验证器检查
   ├─ 通过 → 完成
   └─ 失败 → 提供反馈 → Agent重新执行
```

验证器可以是：

- 单元测试；
- Linter；
- Schema验证；
- 安全扫描；
- 规则引擎；
- LLM Judge；
- 人工审批。

LangChain把验证循环描述为在Agent外增加Grader，并在不符合规则时把反馈送回Agent；代价则是增加延迟和成本。[LangChain](https://www.langchain.com/blog/the-art-of-loop-engineering)

------

### 3.3 Event-driven Loop：事件循环

```
新事件到达
→ Agent运行
→ 更新状态
→ 等待下一事件
```

触发源包括：

- 定时器；
- 新邮件；
- Slack消息；
- 文件上传；
- GitHub Issue；
- Webhook；
- 数据库变更；
- 监控告警。

这类Agent不是一次性聊天，而是持续存在的系统组件。[LangChain](https://www.langchain.com/blog/the-art-of-loop-engineering)

OpenClaw中的定时任务、心跳、Hook和看门狗都可以被理解为这一层。

------

### 3.4 Improvement Loop：改进循环

```
大量运行轨迹
   ↓
分析失败模式
   ↓
修改提示词、工具、规则、Graph或评估器
   ↓
重新部署
   ↓
收集新轨迹
```

这不再是“Agent完成任务”，而是“系统改进Agent本身”。

LangChain称之为Hill-climbing Loop：分析运行轨迹，识别问题，并更新提示词、工具或评分规则，使内层循环逐步改善。[LangChain](https://www.langchain.com/blog/the-art-of-loop-engineering)

------

## 4. Loop Engineering的设计原则

Loop Engineering不是简单写一个`while`。

### 4.1 明确循环不变量

每轮执行后，必须保持某些条件：

```
已完成任务不能重新变成未完成
已经确认的用户信息不能丢失
预算不能增加
重试次数只能增加
外部操作必须可追踪
```

------

### 4.2 每轮必须产生可衡量的进展

错误设计：

```
思考 → 再思考 → 再思考
```

良好设计：

```
每轮至少完成一个：
- 消除一个未知项
- 完成一个子任务
- 获取一个新证据
- 修复一个失败
- 缩小候选范围
```

可以定义进度函数：

```
Progress =
已完成子任务数
+ 已验证假设数
+ 已消除错误数
- 新增未解决问题数
```

若连续若干轮没有进展，应中止、改变策略或交给人工。

------

### 4.3 设置多重停止条件

不要只依赖模型自己说“完成了”。

应同时考虑：

```
模型声明完成
AND 验证器通过
AND 必需产物存在
AND 没有未完成子任务
AND 没有超过成本上限
```

常见硬停止条件：

- 最大轮数；
- 最大Token；
- 最大费用；
- 最大执行时间；
- 最大工具调用数；
- 相同错误重复次数；
- 无进展轮数；
- 人工取消。

------

### 4.4 操作必须幂等

幂等是指同一个操作执行两次，不会产生不可控的重复结果。

例如：

不安全：

```
每次重试都发送一次付款
```

较安全：

```
用 transaction_id 检查付款是否已执行；
未执行才提交。
```

智能体循环中，网络超时不代表操作失败。如果直接重试，可能产生：

- 重复付款；
- 重复邮件；
- 重复建单；
- 重复删除；
- 重复提交PR。

------

### 4.5 区分可逆动作与不可逆动作

可逆动作：

- 读取文件；
- 搜索；
- 创建草稿；
- 在沙盒中修改；
- 创建临时分支。

不可逆或高风险动作：

- 删除生产数据；
- 发送正式邮件；
- 合并PR；
- 支付；
- 发布内容；
- 修改访问权限。

不可逆动作前应设置Graph审批节点，而不是让循环自行决定。

------

## 5. Loop常见失败模式

### 无限循环

模型不断：

```
搜索 → 信息不足 → 再搜索
```

但没有定义“足够”的标准。

### 上下文膨胀

每轮把全部历史重新放入上下文，最终导致：

- 成本上升；
- 延迟增加；
- 注意力分散；
- 早期关键信息被淹没。

### 振荡

```
方案A → 发现问题 → 改为B
方案B → 发现问题 → 又改回A
```

需要保存“已尝试策略”和失败原因。

### 自我验证偏差

同一个模型既生成又评分，容易认可自己的错误。

重要任务应使用：

- 确定性测试；
- 独立模型；
- 不同提示词；
- 外部事实源；
- 人工审批。

### 局部最优

循环不断优化格式，却没有解决任务本身。

因此验证指标必须与真正目标对齐。

------

# 四、Graph Engineering：图工程

## 1. 定义

在当前AI Agent语境下，可以定义为：

> **Graph Engineering是把任务、智能体、工具、验证器、人工审批和反馈循环设计为一个显式、可执行、可观察、可恢复的有状态图。**

它关注的不是某一个节点如何写提示词，而是：

```
系统有哪些节点？
节点职责如何划分？
状态如何流动？
谁决定下一步？
哪里并行？
哪里循环？
哪里必须确定性执行？
哪里允许模型自主判断？
哪里需要人工审批？
失败后如何恢复？
```

LangChain对这一概念的概括是：通过Graph对系统路径施加结构化约束，在适合的位置保留Agent自主性，而不是把所有下一步决策都交给模型。[LangChain](https://www.langchain.com/blog/3-years-of-graph-engineering-with-langgraph)

------

## 2. Graph Engineering的核心工作

### 2.1 节点划分

节点太大：

```
一个Agent完成分析、编码、测试、发布
```

问题：

- 无法定位失败；
- 权限过大；
- 难以替换；
- 重试成本高；
- 状态不透明。

节点太小：

```
每读取一行代码都是一个节点
```

问题：

- 调度开销高；
- Graph极其复杂；
- 状态传递频繁；
- 难以理解。

理想节点应当是：

> 有明确输入、明确产物、能够独立验证、适合单独重试的工作单元。

------

### 2.2 确定性与Agentic边界

这是Graph Engineering中最重要的设计决策之一。

应使用确定性程序的地方：

- 权限检查；
- 金额限制；
- 数据格式；
- 测试结果；
- 状态机转换；
- 文件是否存在；
- API返回码；
- 用户是否批准。

适合交给LLM的地方：

- 问题分类；
- 方案生成；
- 语义判断；
- 信息提取；
- 解释错误；
- 规划下一步；
- 综合多来源材料。

基本原则：

> **事实条件用代码判断，模糊语义用模型判断。**

------

### 2.3 状态Schema设计

不要只保存聊天消息。

应显式定义：

```
class AgentState:
    task_id: str
    objective: str
    plan: list
    completed_steps: list
    evidence: list
    artifacts: list
    errors: list
    retry_count: int
    budget_used: float
    approval_status: str
```

结构化状态能够减少模型从长对话里“猜当前进度”。

------

### 2.4 分支与路由

好的路由应回答：

- 哪些条件进入下一节点？
- 条件由代码判断还是模型判断？
- 模型路由结果是否需要置信度？
- 低置信度时怎么处理？
- 是否有默认路径？
- 是否可能进入无法结束的路径？

例如：

```
置信度 ≥ 0.85 → 自动路由
0.50～0.85    → 追加检索后再判断
< 0.50        → 请求人工选择
```

------

### 2.5 并行与汇合

并行任务要解决两个问题：

**拆分**

```
哪些子任务相互独立？
```

**汇合**

```
结果冲突时由谁裁决？
缺少一个结果能否继续？
等待全部结果还是满足多数即可？
```

例如研究Agent：

```
法规来源 ─┐
行业报告 ─┼→ 证据去重 → 冲突检测 → 综合报告
论文来源 ─┘
```

------

### 2.6 重试、回退与补偿

节点失败后并不只有“再执行一次”。

可采用：

```
同参数重试
修改参数重试
更换工具
更换模型
切换备用数据源
回退到上一个检查点
请求人工介入
执行补偿操作
```

补偿操作类似分布式系统中的Saga：

```
创建订单成功
扣款成功
库存锁定失败
→ 退款
→ 取消订单
```

对于会操作真实系统的Agent，补偿路径与成功路径同样重要。

------

### 2.7 可观察性

每个节点应记录：

```
trace_id
task_id
node_name
input_summary
output_summary
model
token_usage
tool_calls
duration
retry_count
error_type
state_diff
decision_reason
```

尤其建议记录**状态差异**，而不是每次保存完整状态：

```
retry_count: 1 → 2
approval_status: pending → approved
modified_files: +auth.py
```

------

## 3. Graph Engineering适用场景

适合：

- 有明确业务阶段；
- 存在审批和权限边界；
- 任务需要长时间运行；
- 必须从失败中恢复；
- 有多个Agent或工具；
- 需要并行处理；
- 需要审计；
- 不允许模型完全自由行动。

典型场景：

- 编码Agent；
- 企业客服；
- 法律合规；
- 财务审批；
- 文档处理；
- RPA自动化；
- 供应链流程；
- 多来源研究；
- 安全事件响应。

不一定需要Graph的场景：

- 简单问答；
- 一次性文本改写；
- 单次分类；
- 简单摘要；
- 一个工具即可完成的确定性任务。

不要为了“架构先进”把三步流程设计成几十个节点。

------

## 4. Graph Engineering与知识图谱工程的区别

“Graph Engineering”存在语义歧义。

### 智能体Graph Engineering

研究：

```
任务节点、控制流、状态、循环、并行和调度
```

### Knowledge Graph Engineering

研究：

```
实体、关系、本体、Schema、图数据库、图查询和知识治理
```

例如：

```
《民法典》—包含→ 合同编
合同编—规定→ 违约责任
某司法解释—解释→ 某条款
```

知识图谱可以作为Agent Graph中的一个检索节点，但两者不是同一件事：

```
执行Graph：控制Agent怎么工作
知识Graph：表示Agent知道什么
```

------

# 五、Harness Engineering：智能体支架/运行外壳工程

## 1. Harness是什么意思

Harness原义是“马具、线束、约束装置”。在AI Agent领域，它表示：

> 围绕模型建立的一整套工具、运行时、上下文、控制、验证和安全基础设施。

LangChain给出的直接定义是：

```
Agent = Model + Harness
```

并把Harness概括为模型之外的代码、配置和执行逻辑，包括系统提示词、工具、Skill、MCP、文件系统、沙盒、编排逻辑、Hook和中间件。[LangChain](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

------

## 2. Harness包含什么

一个成熟Harness通常包括以下层面。

### 2.1 指令系统

- System Prompt；
- AGENTS.md；
- 项目规范；
- 编码规则；
- 领域术语；
- 操作边界；
- 任务完成标准。

------

### 2.2 上下文系统

- 对话历史；
- 当前任务状态；
- 项目文档；
- 文件索引；
- 短期记忆；
- 长期记忆；
- RAG；
- Context压缩；
- Progressive Disclosure，渐进式披露。

OpenAI在Codex实践中没有把所有知识堆进一个庞大的`AGENTS.md`，而是把它作为目录，让Agent逐步读取结构化、版本化的项目文档；同时通过Linter和CI检查文档新鲜度与结构。[OpenAI](https://openai.com/index/harness-engineering/)

------

### 2.3 工具系统

- 文件读写；
- 命令行；
- 浏览器；
- 数据库；
- Git；
- 邮件；
- 日历；
- API；
- MCP；
- Skill；
- 搜索；
- 代码执行。

工具不仅需要“存在”，还要有：

- 清晰描述；
- 结构化参数；
- 权限限制；
- 超时；
- 重试策略；
- 返回Schema；
- 错误信息；
- 审计日志。

------

### 2.4 执行环境

- 沙盒；
- 容器；
- 虚拟机；
- 临时工作区；
- Git worktree；
- 依赖管理；
- 网络策略；
- Secret管理；
- CPU、内存和磁盘限制。

模型本身不能执行代码、访问实时信息或维护持久状态，这些能力都由Harness提供。[LangChain](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

------

### 2.5 编排系统

Harness中通常包含：

- Agent Loop；
- Graph；
- 子Agent；
- 任务队列；
- 路由；
- 模型选择；
- 并行执行；
- 检查点；
- 暂停与恢复。

所以从范围上看：

```
Loop Engineering  ⊂ Harness Engineering
Graph Engineering ⊂ Harness Engineering
```

这不是严格学术集合关系，而是非常实用的工程理解。

------

### 2.6 安全与权限

- 最小权限；
- 工具白名单；
- 敏感操作确认；
- 路径限制；
- 网络出口限制；
- Secret隔离；
- 数据脱敏；
- 审批；
- 速率限制；
- 预算限制。

例如：

```
读取仓库：自动允许
修改分支：自动允许
推送远程：需要审批
合并主分支：必须人工批准
删除生产数据：禁止
```

------

### 2.7 验证系统

- 单元测试；
- 集成测试；
- 类型检查；
- Linter；
- 安全扫描；
- 业务规则；
- LLM Judge；
- 人工Review；
- 验收标准；
- 回归测试集。

------

### 2.8 可观察性

- Trace；
- 日志；
- Token；
- 成本；
- 延迟；
- 工具成功率；
- 节点失败率；
- 重试次数；
- 任务完成率；
- 人工介入率；
- 输出质量分。

------

### 2.9 反馈和自我改进

当Agent失败时，不应只修改提示词，而应判断失败属于哪一层：

```
缺少知识       → 改上下文/RAG
工具不会使用   → 改工具描述或Skill
工具能力不足   → 新增工具
路径错误       → 改Graph
反复失败       → 改Loop和停止条件
越权操作       → 改权限和Guardrail
无法判断完成   → 改验证器
项目难理解     → 改文档与代码结构
```

OpenAI的Harness Engineering实践强调：Agent失败时，重点不是要求模型“更努力”，而是识别缺失的能力、工具、结构、约束或可读信息，并把解决方案编码到环境中。[OpenAI](https://openai.com/index/harness-engineering/)

------

## 3. Harness Engineering的核心设计原则

### Agent Legibility：对Agent可读

人能理解，不代表Agent能理解。

Agent需要：

- 明确目录；
- 结构化文档；
- 可检索的决策记录；
- 可执行的测试；
- 清晰错误消息；
- 稳定工具Schema；
- 明确完成标准。

OpenAI将“Agent legibility”作为核心目标：凡是运行时无法访问的知识，对Agent而言实际上等于不存在。[OpenAI](https://openai.com/index/harness-engineering/)

------

### Enforceability：规则可执行

弱规则：

```
请保持良好的架构。
```

强规则：

```
禁止跨层依赖；
由结构测试和自定义Linter自动检查。
```

弱规则依赖模型记住，强规则由系统强制执行。

OpenAI的实践包括通过自定义Linter、结构测试、命名约束、文件大小限制和带修复说明的错误消息，把架构规则直接编码到开发环境。[OpenAI](https://openai.com/index/harness-engineering/)

------

### Progressive Disclosure：渐进式披露

不要一开始把所有信息全部塞给模型。

```
入口说明
→ 目录
→ 任务相关文档
→ 具体实现
→ 必要历史记录
```

这样可以降低：

- Token消耗；
- 上下文噪声；
- 错误检索；
- 过时规则干扰。

------

### Reproducibility：可复现

一次Agent运行最好能够重放：

```
模型版本
提示词版本
工具版本
输入数据
环境版本
随机参数
执行轨迹
输出产物
```

否则无法判断改动为什么变好或变差。

------

### Model Replaceability：模型可替换

Harness不应与单一模型深度绑定。

理想状态：

```
GPT模型
Claude模型
本地模型
小模型
```

可以在相同Graph、工具和验证体系中替换，只针对能力差异做少量调整。

------

# 六、四个词的关键区别

| 概念                | 主要研究对象         | 核心问题                         | 典型产物                                  |
| ------------------- | -------------------- | -------------------------------- | ----------------------------------------- |
| Graph               | 节点和边构成的结构   | 系统有哪些步骤，如何连接         | 状态图、DAG、工作流                       |
| Loop                | 反复执行的反馈过程   | 当前结果不好时，下一轮怎么做     | Agent循环、验证循环、重试循环             |
| Graph Engineering   | 整个执行拓扑         | 如何组织多步骤、多Agent、多循环  | 节点设计、路由、状态Schema、检查点        |
| Harness Engineering | 模型外部完整运行系统 | 怎样让模型稳定、安全、高效地工作 | 工具、沙盒、Graph、Loop、权限、评估、日志 |

------

# 七、与Prompt Engineering、Context Engineering的关系

可以用下面五层理解：

| 层级                | 解决的问题                             |
| ------------------- | -------------------------------------- |
| Prompt Engineering  | 这一轮应该怎样向模型表达任务           |
| Context Engineering | 这一轮应该让模型看到什么               |
| Loop Engineering    | 模型完成一步以后，下一轮如何继续       |
| Graph Engineering   | 多个步骤、Agent和循环如何组织          |
| Harness Engineering | 整个系统如何运行、约束、验证和持续改进 |

注意它们不是互相替代，而是逐层扩展：

```
Prompt
  ↓
Context
  ↓
Loop
  ↓
Graph
  ↓
Harness
```

更准确地说：

- Prompt是Harness中的指令部件；
- Context是Harness中的信息供给系统；
- Loop是Harness中的时间控制机制；
- Graph是Harness中的结构化编排机制；
- Harness是它们共同运行的总体系统。

# 八、用OpenClaw法律法规同步Agent举例

假设建立一个持续同步国家法律法规的智能体。

## Harness层

包含：

```
浏览器工具
下载工具
文件系统
法规网站白名单
定时器
代理配置
登录Cookie
OCR
文本解析器
数据库
向量索引
邮件通知
日志
权限规则
失败告警
看门狗
```

## Graph层

```
定时触发
   ↓
检查网站
   ↓
发现新法规？
   ├─ 否 → 记录检查结果 → 结束
   └─ 是
       ↓
     下载正文与附件
       ↓
     解析文本
       ↓
     去重与版本比较
       ↓
     有效性验证
       ├─ 不确定 → 人工审核
       └─ 通过
           ↓
         更新知识库
           ↓
         重建索引
           ↓
         发送通知
```

## Loop层

### 分页循环

```
读取第1页 → 第2页 → 第3页 → 直到没有下一页
```

### 下载重试循环

```
主接口失败
→ 重试
→ 更换备用接口
→ 浏览器下载
→ 超过上限后告警
```

### 验证循环

```
解析文本
→ 检查标题、文号、发布日期、正文
→ 字段缺失
→ 重新解析或OCR
→ 再验证
```

### 改进循环

```
分析一个月内失败日志
→ 发现附件解析失败率高
→ 改解析Skill
→ 运行回归测试
→ 部署新版本
```

这时：

- **Graph**定义整体业务路径；
- **Loop**解决分页、重试和质量迭代；
- **Harness**提供浏览器、权限、文件、调度、日志、看门狗和验证环境；
- **Graph Engineering**负责把这些组件组织成可恢复、可审计的系统。

# 九、实际选型原则

## 只需要Loop

任务开放，但结构很简单：

```
模型 → 工具 → 模型 → 完成
```

例如：

- 查询资料；
- 修复一个小Bug；
- 分析一个文件夹；
- 执行一次简单RPA任务。

## 需要Graph

任务有明确阶段、分支或审批：

- 规划、执行、验证；
- 多类型请求路由；
- 多Agent协作；
- 并行处理；
- 失败补偿；
- 人工审批。

## 需要完整Harness Engineering

当系统进入长期或生产运行：

- 有真实权限；
- 操作文件、数据库、邮件或生产环境；
- 需要安全控制；
- 需要成本治理；
- 需要评估和审计；
- 需要持续改进；
- 需要更换模型；
- 需要多人维护。

------

# 十、最终结论

这四个概念不是平行的四种技术，而是不同层级的工程抽象：

```
Model提供智能
Loop提供反馈
Graph提供结构
Harness提供能力、边界和运行保障
```

其中：

> **Loop决定Agent是否能持续行动；Graph决定复杂任务是否可控；Harness决定整个系统是否能进入生产环境。**

从工程范围看：

```
Harness Engineering
├── Prompt与Context设计
├── Tool、Skill、MCP设计
├── Loop Engineering
├── Graph Engineering
├── Memory
├── Sandbox与权限
├── Observability
├── Evaluation
└── 持续改进
```

对你目前关注的OpenClaw、Skill、MCP、Hook、看门狗和长期记忆系统来说，最适合的理解是：

- **Skill/MCP/工具**是Harness提供的能力；
- **Hook/Guardrail**是Harness提供的确定性控制；
- **Agent Loop**是智能体执行的基本发动机；
- **看门狗/心跳/定时任务**属于外层事件Loop；
- **Graph**负责把Agent、工具、验证、人工审批和错误恢复连接起来；
- **Harness Engineering**则是把以上全部设计成一个长期可靠运行的系统。

这是目前开源 Agent 圈最值得研究的问题之一。

很多人在部署 **GPT-OSS（例如 gpt-oss-20B/120B）、Qwen、DeepSeek、Llama、Mistral** 时都会发现：

> **同样一套 Harness，GPT-5、Claude 能跑得很好，而中小模型却表现很差。**

很多人因此得出结论：

> **Harness 对小模型没用。**

实际上，我认为这是一个误区。

真正的问题是：

> **现在大多数 Harness 都是按照 GPT-5、Claude Sonnet、Gemini 2.5 Pro 这种"高能力模型"设计的，而不是按照"低能力模型"设计的。**

它们默认假设模型拥有很强的推理能力、自我纠错能力和长上下文管理能力，而低能力模型往往不具备这些能力。

------

# 为什么低能力模型使用 Harness 效果不好？

先看 Harness 的标准流程：

```
用户任务
     │
 Planner
     │
 Executor
     │
 Tool
     │
 Reflection
     │
 Judge
     │
 Retry
```

GPT-5 在每个节点都能稳定工作。

例如：

Planner：

```
应该拆成四个步骤
```

Executor：

```
先执行 Tool A
再执行 Tool B
```

Reflection：

```
Tool B 输出异常
需要重新执行
```

Judge：

```
测试没有通过
```

Retry：

```
修改方案
重新执行
```

整个流程都比较稳定。

------

但 GPT-OSS 这类模型通常不是这样。

例如 Planner：

```
不知道怎么拆
```

Reflection：

```
看不出来哪里错
```

Judge：

```
测试失败

↓

仍然认为成功
```

Retry：

```
重复第一次方案
```

于是：

Harness 没有发挥作用。

反而：

越来越慢。

Token越来越多。

错误越来越多。

------

## 为什么？

因为 Harness 默认假设：

> **模型能够理解整个 Workflow。**

但是：

GPT-OSS 很多时候：

连当前一步都容易理解错。

所以：

不是 Harness 有问题。

而是：

**Harness 太相信模型。**

------

# GPT-OSS 最大的问题不是知识，而是控制能力

很多测试发现：

GPT-OSS：

知识：

★★★★☆

推理：

★★★☆☆

工具使用：

★★☆☆☆

长期规划：

★☆☆☆☆

★☆☆☆☆

★☆☆☆☆

# 那应该怎样升级 Harness？

我认为未来会出现一种新的方向：

> **Small Model Harness（SMH）**

不是：

让模型负责全部。

而是：

把大量决策收回 Harness。

下面我认为有几个方向。

------

# 第一：把 Planner 拆掉（最重要）

现在很多 Agent：

```
Planner

↓

生成完整计划

↓

Executor
```

GPT-5 可以。

GPT-OSS 不行。

建议：

改成：

```
Task

↓

Step Generator

↓

一步

↓

执行

↓

再生成下一步
```

不要：

一次规划：

十步。

改成：

每次：

只规划一步。

例如：

不要：

```
修改整个项目
```

而是：

```
第一步：

找到Bug。

↓

完成。

↓

第二步：

修改Bug。

↓

完成。

↓

第三步：

运行测试。
```

为什么？

因为：

小模型：

更适合：

短期规划。

------

# 第二：Harness 接管 Reflection

很多 Harness：

Reflection：

还是：

LLM。

例如：

```
为什么失败？
```

GPT-OSS：

回答：

```
可能网络不好。
```

其实：

真正原因：

```
404
```

所以：

不要：

让模型分析日志。

改成：

Harness：

直接：

解析：

```
ExitCode

HTTP

stderr

stdout

pytest
```

例如：

```
pytest:

FAILED

↓

Harness：

定位：

test_login.py

Line 83

↓

告诉模型：

修这里。
```

而不是：

把：

1000行日志：

交给模型。

------

# 第三：增加 Rule Engine（规则引擎）

很多判断：

根本不需要模型。

例如：

```
Git 有没有冲突？

↓

Git自己知道。

↓

Docker自己知道。
文件是否存在？

↓

OS知道。

↓

程序知道。
```

所以：

Rule Engine：

应该越来越强。

模型：

越来越少判断。

------

# 第四：状态压缩（Memory Compression）

GPT-OSS：

上下文：

容易爆。

所以：

不要：

全部Memory。

建议：

每一步：

自动：

压缩。

例如：

原来：

```

```

变成：

```

已完成：

4

5
```

而不是：

一直：

追加。

------

# 第五：Tool Router

GPT-OSS：

最容易：

工具乱选。

例如：

不知道：

------

# 第六：模板化 Tool 调用

很多模型：

而是：

# 第七：把 Retry 变成 Search

# 我认为未来针对 GPT-OSS 这类模型的 Harness 设计原则可以概括为一句话

高能力模型（GPT-5、Claude）适合：

> **Think More（多思考，少约束）**

它们可以承担规划、反思、纠错等复杂认知任务。

而低能力模型（GPT-OSS、7B～32B 开源模型）更适合：

> **Think Less，Execute Better（少思考，多执行）**

Harness 应尽可能把**规划、规则判断、状态管理、工具选择、错误定位、经验复用**这些确定性工作从模型手中收回，用程序完成；模型只负责局部推理和生成。这种"厚 Runtime + 轻模型"的架构，比单纯提升模型参数规模，更有可能让中小模型在生产环境中获得稳定、可预测的表现。
