## 核心结论

Codex 的任务工作流并不是传统的：

> 需求 → 编码 → 测试 → 完成

这种固定流水线，也不是预先写死的 DAG。

它采用的是：

> **外层任务编排器 + 内层 Agent Loop + 工具执行沙盒 + 验证反馈回路**

其中，**Agent Loop 是核心执行管道**；Project、Thread、Worktree、子代理和后台任务属于外层编排系统。OpenAI 将负责这套循环与执行逻辑的部分称为 **Codex Harness**。[OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)

------

# 一、Codex 的整体任务管道

可以将 Codex 的工作流程抽象为：

```
用户任务
   │
   ▼
Codex App / IDE / CLI
   │
   ▼
App Server
   │
   ├── Project 管理
   ├── Thread 管理
   ├── Turn 管理
   ├── 状态持久化
   └── 事件流输出
   │
   ▼
Codex Core / Harness
   │
   ▼
上下文构建
   │
   ├── 系统指令
   ├── 开发者指令
   ├── 用户任务
   ├── 项目环境
   ├── 对话历史
   ├── Skills
   ├── 工具定义
   └── 沙盒与权限策略
   │
   ▼
模型推理
   │
   ├── 直接回答 ───────────────┐
   │                           │
   └── 请求工具调用             │
          │                    │
          ▼                    │
   权限检查 / 用户审批          │
          │                    │
          ▼                    │
   Shell / Git / MCP / 浏览器   │
          │                    │
          ▼                    │
   工具执行结果写回上下文        │
          │                    │
          └──── 再次模型推理 ───┘
   │
   ▼
测试 / 检查 / 修复循环
   │
   ▼
生成 Diff、文件、测试结果和总结
   │
   ▼
用户审查、继续修改或提交
```

真正反复运行的是这一段：

```
推理 → 调用工具 → 获取结果 → 更新上下文 → 再推理
```

直到模型不再请求工具，而是输出最终的 assistant message，当前 Turn 才结束。[OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)

------

# 二、任务在 Codex 中的层级结构

Codex 的任务状态主要分为几个层级。

## 1. Project

Project 是项目级容器，通常对应一个代码库或长期工作空间。

它承载：

- 仓库位置；
- 项目配置；
- Skills；
- 会话历史；
- 多个并行任务；
- Git worktree；
- 项目权限和运行环境。

Codex App 按 Project 组织多个代理线程，使不同任务可以并行执行而不丢失各自上下文。[OpenAI](https://openai.com/index/introducing-the-codex-app/)

------

## 2. Thread

Thread 是一条持续的任务会话，可以理解为：

> 一个代理负责的一条完整工作线。

例如：

```
Thread A：修复 OCR 表格识别问题
Thread B：迁移 PySide6 版本
Thread C：检查打包启动速度
Thread D：重构翻译模块
```

每条 Thread 都保存自己的：

- 对话历史；
- 工具调用；
- 文件修改；
- 测试结果；
  -审批状态；
  -任务进度。

Codex Core 会为每个 Thread 创建一个独立 Core Session，由 Thread Manager 管理。[OpenAI](https://openai.com/index/unlocking-the-codex-harness/)

------

## 3. Turn

Turn 是一次“用户输入—代理完成—控制权返回”的完整周期。

例如：

```
用户：
修复程序启动时托盘图标不一致的问题

Codex：
读取代码
搜索托盘初始化逻辑
修改状态同步代码
运行测试
检查 Git diff
输出完成说明
```

这一整段属于一个 Turn。

需要注意：

> 一个 Turn 内部可以包含几十次甚至几百次“模型推理—工具调用”。

因此，Turn 不是一次模型调用，而是一次完整的任务交互周期。[OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)

------

## 4. Item

Item 是 Thread 和 Turn 中的最小事件对象，例如：

- 用户消息；
- 模型推理摘要；
- Shell 调用；
- Shell 输出；
- 文件修改；
- 审批请求；
- 测试结果；
- 最终消息。

Codex App Server 将这些 Item 通过事件流发送给前端，因此用户能实时看到：

```
正在读取文件
正在运行命令
等待授权
测试失败
正在修复
任务完成
```

App Server 会发送 `thread/started`、`turn/started`、工具调用 Item、审批请求以及最终的 `turn/completed` 等事件。[OpenAI](https://openai.com/index/unlocking-the-codex-harness/)

------

# 三、单个任务的内部执行流程

## 阶段一：任务接收与上下文构建

用户提交任务后，Codex 不会只把用户文字原样发给模型，而是会构建一个完整的任务上下文。

大致包含：

```
System Instructions
Developer Instructions
Sandbox Policy
Approval Policy
Available Tools
MCP Tools
Working Directory
Shell Type
Project Context
Conversation History
User Request
```

Codex 还会把当前工作目录和 Shell 环境传给模型，例如：

```
<environment_context>
  <cwd>D:\Projects\SightOCR</cwd>
  <shell>powershell</shell>
</environment_context>
```

这样模型才知道：

- 当前位于哪个项目；
- 可以调用什么工具；
- 哪些目录允许修改；
- 哪些行为必须审批；
- 应该使用 PowerShell、Bash 还是其他 Shell。[OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)

因此，Codex 的真实输入更像：

```
基础行为规则
+ 项目规则
+ 环境信息
+ 工具能力
+ 权限边界
+ 历史状态
+ 用户任务
```

而不仅仅是一句 Prompt。

------

## 阶段二：任务理解与动态规划

模型收到上下文后，会先判断：

- 用户真正想解决什么；
- 是否需要读取代码；
- 涉及哪些模块；
- 是否存在风险；
- 是否需要先制定计划；
- 是否需要向用户提问；
- 是否需要运行构建和测试。

对于小任务，它可能直接开始：

```
搜索代码 → 修改 → 测试
```

对于大型任务，可以进入 Plan Mode：

```
需求分析
   ↓
代码库调查
   ↓
拆分里程碑
   ↓
确定修改范围
   ↓
明确验证方法
   ↓
用户审查方案
   ↓
开始实现
```

Codex App、CLI 和 IDE 已支持原生 Plan Mode，用于在修改文件前把复杂任务拆成可审查步骤。[OpenAI Developers](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)

这里很关键：

> **Plan 并不是强制固定流程，而是模型根据任务复杂度动态生成的临时执行图。**

所以 Codex 更接近“动态规划器”，不是传统工作流引擎。

------

## 阶段三：信息探索

Codex 通常不会立即修改代码，而会先形成对代码库的局部认知：

```
列出目录
   ↓
搜索符号或关键词
   ↓
读取入口文件
   ↓
读取相关模块
   ↓
检查测试文件
   ↓
检查 Git 状态
   ↓
定位依赖关系
```

例如修复 SightOCR 的托盘状态问题时，它可能依次执行：

```
Get-ChildItem -Recurse
rg "tray" .
rg "startup" .
Get-Content src\tray_manager.py
Get-Content src\settings.py
git status
```

每个命令结果都会被写回 Agent Loop，模型再基于新信息决定下一步。

这个设计的本质是：

```
模型不必一次性掌握整个仓库
而是通过工具按需获取证据
```

------

## 阶段四：工具决策与执行

模型不能直接操作系统。它只能输出结构化工具请求，例如：

```
{
  "name": "shell",
  "arguments": {
    "command": ["pytest", "tests/test_tray.py"],
    "workdir": "D:\\Projects\\SightOCR"
  }
}
```

Harness 收到请求后负责：

1. 校验工具参数；
2. 检查沙盒策略；
3. 检查审批策略；
4. 执行命令；
5. 捕获 stdout、stderr 和退出码；
6. 将结果作为 tool output 写回模型上下文。

这相当于：

```
LLM = 决策层
Harness = 控制层
Tool = 执行层
Sandbox = 安全边界
```

模型负责判断“做什么”，Harness 负责决定“能不能做、怎么执行、结果如何返回”。

------

# 四、沙盒与审批管道

Codex 不会默认允许代理无限制执行任意操作。

典型流程是：

```
模型请求操作
   ↓
策略判断
   ├── 沙盒内安全操作 → 自动执行
   ├── 超出沙盒边界 → 请求审批
   └── 明确禁止 → 拒绝执行
```

审批请求会暂停当前 Turn，直到用户选择：

```
Allow
Deny
```

然后任务才继续运行。[OpenAI](https://openai.com/index/unlocking-the-codex-harness/)

需要特别注意：

> Codex 自身的沙盒主要约束其内置 Shell 工具；MCP Server 提供的工具不一定自动受 Codex Shell 沙盒保护，需要 MCP 服务自身实施权限控制和安全边界。[OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)

这意味着：

```
Shell Tool
  └── Codex Sandbox 负责约束

MCP Tool
  └── MCP Server 自己负责授权、审计和隔离
```

因此，MCP 并不是天然安全的。

------

# 五、修改—测试—修复反馈环

Codex 的代码修改也不是“一次生成后结束”，而是一个反馈控制系统：

```
分析问题
   ↓
修改代码
   ↓
运行测试
   ↓
读取错误
   ↓
重新定位
   ↓
再次修改
   ↓
重新测试
   ↓
检查 Diff
```

可以抽象成：

```
Action → Observation → Evaluation → Correction
```

例如：

```
修改 tray_manager.py
        ↓
运行 pytest
        ↓
发现状态同步测试失败
        ↓
读取 settings_manager.py
        ↓
修复初始化顺序
        ↓
再次运行测试
        ↓
通过
```

这也是 Codex 和普通代码补全工具的主要区别：

- 普通补全工具主要生成候选代码；
- Codex 会操作环境、观察结果并自我修正。

不过，Codex Core 并不存在一个绝对独立、永远可靠的“测试阶段”。是否运行哪些验证，仍然由模型、任务指令和项目规范共同决定。

因此，项目必须明确提供：

```
测试命令
构建命令
Lint 命令
验收标准
禁止修改范围
```

否则代理可能只做它认为足够的验证。

# 六、长任务为什么需要里程碑管道

大型任务如果持续运行很久，会出现：

- 上下文膨胀；
- 目标漂移；
- 修改范围扩大；
- 前面决策被遗忘；
- 测试集中到最后；
- 失败后难以定位；
- 重启后状态难以恢复。

因此更可靠的长任务管道是：

```
需求
  ↓
总体 Plan
  ↓
Milestone 1
  ├── 实现
  ├── 测试
  ├── 修复
  └── 更新状态
  ↓
Milestone 2
  ├── 实现
  ├── 测试
  ├── 修复
  └── 更新状态
  ↓
Milestone 3
  ↓
集成验证
  ↓
交付
```

OpenAI 给出的长周期任务实践也是：

- Plan 作为事实来源；
- 每个里程碑完成后立即验证；
- 测试失败立即修复；
- 控制 Diff 范围；
- 持续更新状态和决策文档。[OpenAI Developers](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)

这实际形成了一个双层循环：

```
外循环：里程碑推进

内循环：
实现 → 测试 → 诊断 → 修复
```

------

# 七、上下文管理管道

Codex 每次继续对话时，会把之前的：

- 用户消息；
- 模型消息；
- 推理项；
- 工具调用；
- 工具输出；

继续加入新请求。

因此，随着任务变长，上下文会不断增长。[OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)

其逻辑是：

```
上一轮上下文
+ 上一轮输出
+ 新的用户输入
= 新一轮模型上下文
```

当上下文达到一定阈值时，Codex 会执行自动 Compaction：

```
完整历史
   ↓
压缩
   ↓
保留任务状态、重要决策和模型理解
   ↓
继续运行
```

Codex 使用自动压缩机制避免上下文窗口被长时间工具调用完全占满。[OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)

不过，压缩本质上仍是有损过程，容易损失：

- 边缘约束；
- 早期讨论细节；
- 某些失败原因；
- 临时约定；
- 未记录的设计决策。

因此，长任务中最好将关键状态写入项目文件，而不是只保存在聊天上下文中，例如：

```
PLAN.md
IMPLEMENTATION.md
DECISIONS.md
TESTING.md
PROGRESS.md
```

这属于“外部化工作记忆”。

------

# 八、多代理与子代理的外层编排

单个 Agent Loop 解决的是：

> 一个代理如何完成一个任务。

多代理系统解决的是：

> 多个任务怎样并行推进、隔离并最终合并。

Codex App 的设计是：

```
Project
 ├── Thread A
 │    └── Agent A
 ├── Thread B
 │    └── Agent B
 ├── Thread C
 │    └── Agent C
 └── Thread D
      └── Agent D
```

为了避免多个代理同时修改同一个工作目录，Codex App 使用 Git worktree：

```
主仓库
 ├── worktree-agent-a
 ├── worktree-agent-b
 └── worktree-agent-c
```

每个代理工作在独立代码副本中，然后再进行：

```
Diff Review
   ↓
Commit
   ↓
Cherry-pick / Merge
   ↓
集成测试
```

Codex App 原生支持不同 Thread 和 worktree，使多个代理能够在同一仓库并行工作而尽量避免直接冲突。[OpenAI](https://openai.com/index/introducing-the-codex-app/)

------

# 九、项目级任务调度器

如果任务来源不是人工输入，而是 Issue Tracker、CI 或定时系统，则还会增加一层 Orchestrator：

```
Linear / GitHub Issues / Jira
        ↓
任务轮询
        ↓
任务标准化
        ↓
优先级判断
        ↓
创建 Workspace
        ↓
启动 Codex Thread
        ↓
监控运行状态
        ↓
失败重试
        ↓
生成 PR
        ↓
人工审查
```

OpenAI 的 Symphony 采用的就是这种模式：

```
Issue Tracker = 控制平面
Codex Agent = 执行单元
Workspace = 隔离环境
Orchestrator = 调度器
Human = 最终审查者
```

其 Orchestrator 负责判断哪些 Issue 应该：

- Dispatch；
- Retry；
- Stop；
- Release；
- 回收 Workspace；
- 更新任务状态。[OpenAI](https://openai.com/index/open-source-codex-orchestration-symphony/)

所以完整架构可以理解为：

```
┌────────────────────────────────────┐
│      Project / Issue Orchestrator   │
│ 调度、并发、重试、优先级、生命周期 │
└────────────────┬───────────────────┘
                 │
        ┌────────┴────────┐
        ▼                 ▼
  Codex Thread A     Codex Thread B
        │                 │
  Agent Loop A       Agent Loop B
        │                 │
  Worktree A         Worktree B
```

# 十、为什么 Codex 不采用纯 Graph Engineering

固定 Graph 更适合：

```
输入格式稳定
节点职责明确
执行路径可以提前预测
失败分支有限
```

例如：

```
代码提交
 → Lint
 → Unit Test
 → Security Scan
 → Build
 → Deploy
```

但软件工程任务通常存在大量未知情况：

```
不知道问题在哪个文件
不知道需要调用什么工具
不知道测试会报什么错
不知道是否要回滚
不知道是否需要修改设计
```

所以 Codex 采用：

```
Agent Loop 负责探索和决策
Graph / Workflow 负责外围约束和确定性步骤
```

最合理的组合是：

```
确定性流程使用 Graph

不确定性问题使用 Agent Loop

高风险节点使用人工审批

重复性能力封装为 Skill

外部系统通过 MCP 接入

并行任务交给 Orchestrator
```

这实际上是混合架构：

```
Graph 外壳
    +
Agent Loop 内核
    +
Sandbox 执行层
    +
Human Approval 控制点
```

# 十一、Codex 管道的主要优点

## 1. 动态适应

不需要提前知道所有步骤，模型可以根据工具返回结果动态改变路线。

## 2. 能处理开放式任务

可以执行：

- 探索代码库；
- Debug；
- 重构；
- 迁移；
- 测试修复；
- PR Review；
- 文档生成。

## 3. 可中断和可干预

用户可以在执行过程中：

- 提供新要求；
- 拒绝危险操作；
- 修改计划；
- 评论 Diff；
- 要求重新验证。

## 4. 支持多前端

App Server 将 Codex Core 暴露为稳定事件协议，桌面 App、IDE、CLI 和 Web 可以复用同一套 Harness。App Server 使用 JSON-RPC 风格协议管理 Thread，并持续传递任务事件。[OpenAI](https://openai.com/index/unlocking-the-codex-harness/)

## 5. 并行隔离

不同代理通过独立 Thread 和 worktree 并行工作，减少直接覆盖同一工作目录的风险。

------

# 十二、Codex 管道的盲点

## 1. 规划器和执行器可能是同一个模型

它自己制定计划、自己执行、自己判断是否完成，容易出现：

```
计划错误
   ↓
执行错误
   ↓
自我验证仍认为正确
```

更稳健的架构应增加：

```
Planner
Executor
Reviewer
Verifier
```

角色分离。

------

## 2. 测试选择仍依赖模型

模型可能只运行了单元测试，却没有运行：

- 集成测试；
- 回归测试；
- 性能测试；
- UI 验收；
- 打包测试；
- 安全扫描。

所以必须把验证矩阵明确写进任务规则。

------

## 3. 工具输出可能污染上下文

Shell 输出、网页文本、仓库文件和 MCP 返回内容都可能包含：

- 错误信息；
- 无关内容；
- 恶意指令；
- Prompt Injection；
- 伪造状态。

Harness 必须区分：

```
可信指令
非可信数据
工具观察结果
```

不能把工具输出直接当作高优先级指令。

------

## 4. 长上下文会产生状态漂移

即使有自动压缩，长期任务仍可能：

- 忘记原始约束；
- 重复工作；
- 修改已完成模块；
- 偏离验收目标。

因此需要外部状态文件和里程碑。

------

## 5. 多代理不等于自动协作

多个 worktree 能解决文件隔离，但不能自动解决：

- 架构决策冲突；
- API 接口不一致；
- 数据库迁移冲突；
- 重复实现；
- 最终集成失败。

必须有一个主代理或人工承担 Integration Owner。
